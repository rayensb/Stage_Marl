# Stage MARL → ROS 2 → PX4 → Gazebo Testing Workflow

Adopted 2026-08-20, after a first deployment session found and fixed four
real bugs (see `PHASE2_HANDOFF.md`) but also broke Rule 1 below at least
once and skipped Phases 7-11 outright. This is the standing protocol for
this deployment effort from here on -- not a one-time checklist.

## Mission

The trained MARL policy is considered untested until it has been
demonstrated end-to-end in simulation. Do NOT immediately attempt to make
the neural policy control the drone. Instead, validate the complete
pipeline in layers:

```text
                 ┌──────────────────────┐
                 │   Trained MARL model │
                 │       π(obs)         │
                 └──────────┬───────────┘
                            │ action
                            ▼
                 ┌──────────────────────┐
                 │   Action adapter     │
                 │ policy → ROS/PX4 cmd │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │        ROS 2         │
                 │ topics / nodes / DDS │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │         PX4          │
                 │       SITL           │
                 └──────────┬───────────┘
                            │
                            ▼
                 ┌──────────────────────┐
                 │       Gazebo         │
                 │ physics + sensors    │
                 └──────────┬───────────┘
                            │ observations
                            └───────────────► ROS 2
```

The debugging strategy is: **prove each arrow works before moving to the
next arrow.**

## PHASE 0 — Freeze the environment

Before changing code, determine exactly what is installed and what is
actually being used. Do NOT assume the intended versions are the installed
versions.

Record:

```bash
lsb_release -a
echo "ROS_DISTRO=$ROS_DISTRO"
ros2 --version
gz --version
cd ~/PX4-Autopilot && git rev-parse --short HEAD
python3 --version
which python3
python3 -c "import torch; print(torch.__version__)"
printenv | grep -E 'ROS|PX4|GZ|RMW|CYCLONE|FAST'
ros2 pkg list | grep -E 'px4|ros_gz|gazebo'
```

The final report must contain: Ubuntu version, ROS 2 version, Gazebo
version, PX4 commit/version, Python version, PyTorch version, workspace
path, model checkpoint path, ROS middleware implementation, exact PX4
vehicle model, exact Gazebo world, whether the test is single-agent or
multi-agent.

Never debug a system whose actual versions are unknown.

## PHASE 1 — Validate the trained policy WITHOUT Gazebo

The first question is NOT "Can the drone fly?" The first question is "Can
the exact trained checkpoint be loaded and produce valid actions from the
exact observation representation used during training?"

Create a standalone inference test that: loads the checkpoint, constructs
the same actor architecture used during training, constructs an
observation with exactly the same dimension/order/ranges as training, runs
inference, prints the action, verifies the action is finite, verifies the
action is inside the expected range.

Do not silently create a new observation representation for Gazebo. The
inference adapter must reproduce the training observation semantics
exactly. Test with: zero observation, known synthetic observation, random
valid observation, observations generated by the original environment.

Expected result:

```text
checkpoint loads → observation accepted → policy produces action →
action is finite → action has shape (3,) per agent → action respects bounds
```

If this fails, STOP. Do not touch Gazebo yet.

## PHASE 2 — Validate the policy against the ORIGINAL training environment

Before ROS 2 exists, run the trained policy inside the environment it was
trained on. Run several episodes using the trained checkpoint. Record:
episode reward, final distance to target, collisions, success rate,
episode length, action statistics, per-agent behaviour. Save
`baseline_policy_results.json`.

This gives a reference. If the policy performs well here but fails in
Gazebo, the problem is probably in the deployment/integration layer rather
than the learned policy itself.

## PHASE 3 — Validate Gazebo + PX4 WITHOUT THE RL POLICY

Completely remove the neural network from the equation. Start PX4 SITL +
Gazebo using the known-good procedure for the installed version. Do NOT
immediately add the custom controller. First prove PX4 SITL ↔ Gazebo works:
vehicle appears, is physically simulated, sensors are publishing, PX4
receives simulator data, the estimator becomes healthy, ROS 2 can see PX4
topics if enabled.

```bash
ros2 topic list
ros2 node list
ros2 topic list | grep fmu
ros2 topic info <topic>
ros2 topic echo <topic>
```

Check that data actually changes while the vehicle moves. A topic existing
is NOT proof that the integration works.

## PHASE 4 — Validate ROS 2 ↔ PX4 communication

Test the communication layer independently of the learned policy:
ROS 2 node → command → PX4 → state → ROS 2 node. PX4's ROS 2 integration
uses uXRCE-DDS. Confirm the agent/client connection and successful
synchronization/topic creation. Do not proceed until: ROS 2 sees PX4
topics, ROS 2 can subscribe to state, timestamps are sensible, state
changes when the simulated vehicle changes, the command interface is
known, commands actually reach PX4.

If the project uses `/clock`, verify time handling explicitly
(`use_sim_time=true` where needed). Do not mix simulation time and wall
time accidentally.

## PHASE 5 — Build a MANUAL/DETERMINISTIC CONTROLLER TEST

Before the RL policy, create a tiny deterministic/proportional controller.
The objective is NOT performance -- it's to prove
ROS command → PX4 → Gazebo → vehicle moves as expected. Test one axis at a
time: X, Y, Z, yaw. Record exactly what happens.

This catches the most common integration problems: coordinate-frame
mismatch, NED vs ENU confusion, body frame vs world frame, wrong sign,
wrong units, wrong topic, wrong message type, wrong command semantics,
command scaling errors.

If +X causes movement in -X, do NOT modify the RL model. Fix the
adapter/frame convention.

## PHASE 6 — Establish the coordinate-frame contract

Write this down explicitly, don't leave it implicit. For every vector,
document: frame, units, axis order, sign convention, reference. Do this
for both the policy's observation/action vectors and the ROS/PX4
command/state vectors, then explicitly define the conversions between them.
Do NOT assume a vector called `[x, y, z]` has the same meaning everywhere.

## PHASE 7 — Build the OBSERVATION ADAPTER

Only now should the trained policy receive real Gazebo/PX4 data. The
observation adapter must reproduce the training environment's observation
exactly. For each agent, document: own velocity, relative target, distance
to target, neighbour information, angles, normalization, clipping,
ordering.

Compare TRAINING OBSERVATION vs GAZEBO OBSERVATION element by element. Do
not merely compare dimensions -- a vector can have the correct dimension
and still be completely wrong (e.g. `[x_vel,y_vel,z_vel,rel_x,rel_y,rel_z,...]`
vs `[rel_x,rel_y,rel_z,x_vel,y_vel,z_vel,...]` have the same dimension;
only one is correct).

Create a debug mode that prints, per agent, `index | name | value`, and
compare it against the original environment.

## PHASE 8 — Observation sanity tests

Before allowing the policy to control anything, manually move the
simulated drone and verify the corresponding observation changes
correctly: move +X/+Y/+Z → rel_target changes in the expected direction;
increase velocity +X → vx increases; move neighbour → neighbour-relative
observation changes.

Also test: distance near zero, distance large, velocity near zero,
velocity near maximum, target behind/above/below vehicle, neighbour on
each side. The policy should receive realistic values -- not NaNs, stale
values, wrong signs, or unbounded values.

## PHASE 9 — Compare observation distributions

The policy was trained on a particular distribution. Collect observations
from Gazebo and compare training mean/std/min/max vs Gazebo mean/std/min/max
for every observation dimension. If training saw `vx ≈ [-1, 1]` but Gazebo
produces `vx ≈ [-15, 15]`, the policy is being used outside its training
distribution -- this is an observation-contract problem, not a
Gazebo-control problem.

## PHASE 10 — Validate ACTION ADAPTER

Do NOT send the policy's action directly to PX4 without documenting the
conversion: range conversion → frame conversion → unit conversion → ROS
message → PX4 command. For each action component document: policy
meaning, range, units, frame, PX4 meaning.

Test with artificial actions: `[0,0,0]`, `[+max,0,0]`, `[-max,0,0]`,
`[0,+max,0]`, `[0,-max,0]`, `[0,0,+max]`, `[0,0,-max]`. Observe the actual
vehicle motion -- this is the action equivalent of the observation sanity
test.

## PHASE 11 — Run the policy with COMMAND OUTPUT DISABLED (shadow mode)

Connect everything (Gazebo → PX4 → ROS 2 → observation adapter → policy →
action adapter) but do NOT send actions to PX4. Instead log observation,
policy action, and converted command. Check: no NaNs, no exploding values,
no action saturation, no sudden discontinuities, correct action
dimensions, correct agent/neighbour ordering, correct target, reasonable
inference frequency. Also record policy inference frequency, ROS callback
frequency, sensor frequency, command frequency.

## PHASE 12 — Single-agent closed-loop test

Do NOT start with the full agent count. Start with one: one drone, one
target, no obstacles, no neighbouring agents, simple world. The objective
is only drone → target, not formation control. Produce: initial position,
target position, trajectory, actions, distance-to-target, episode result.
If it fails, stop and diagnose.

## PHASE 13 — Single-agent fault isolation

If the drone behaves incorrectly, classify the failure:

- **Case A -- policy outputs nonsense**: investigate checkpoint,
  architecture, observation order, normalization, preprocessing, PyTorch
  mode, checkpoint loading, training/deployment mismatch.
- **Case B -- policy outputs reasonable actions but drone moves
  incorrectly**: investigate action adapter, coordinate frame, axis order,
  sign, units, PX4 command interface.
- **Case C -- drone moves correctly but policy receives wrong
  observations**: investigate ROS topic, state extraction, timestamp,
  frame transform, sensor data, target calculation.
- **Case D -- everything works individually but closed-loop fails**:
  investigate timing, latency, stale observations, action frequency,
  normalization, distribution shift, policy assumptions.

Never randomly modify the neural network when the evidence points to an
interface problem.

## PHASE 14 — Add the target properly

Define target frame, target position, target update rate, relative-target
calculation, distance calculation -- do not merely hard-code a Gazebo
coordinate and assume it is equivalent. Verify manually: drone moves
toward target → relative target approaches zero → distance decreases. If
the drone physically moves toward the target but the observation says
distance is increasing, the observation transformation is wrong.

## PHASE 15 — Add neighbouring agents

Only after single-agent success. Go 2 → 3 → 4 agents. For each increase,
verify: agent IDs, namespace, PX4 instance, ROS namespace, target
assignment, neighbour ordering, relative positions, action routing. The
most dangerous integration bug here is agent 0's observation feeding
agent 1's policy, whose action then drives agent 0's drone -- add explicit
agent IDs everywhere.

## PHASE 16 — Reproduce the training environment

Match number of agents, initial positions, target positions, velocity
limits, action limits, episode duration, time step, observation limits,
collision distance, safe distance, termination conditions. Treat the
training config values as part of the deployment contract unless there is
a deliberate, documented reason to change them.

## PHASE 17 — Timing verification

Training uses a fixed DT (20 policy steps/second for this project).
Deployment should explicitly establish and *measure* -- not assume --
sensor/update rate, policy rate, command rate, simulation rate, and the
latency from state timestamp → observation received → inference →
command published. A policy trained at one effective control interval can
behave very differently if deployed at another.

## PHASE 18 — Logging

Every closed-loop test must generate enough information to diagnose
failure. At minimum log: timestamp, agent_id, position, velocity,
target_position, relative_target, distance, neighbour observations,
policy action, converted command, episode/step number,
reward-equivalent metrics, collision state, termination reason. Save each
run as `run_YYYYMMDD_HHMMSS/{config.json, observations.csv, actions.csv,
trajectory.csv, events.log, summary.json}`. Never rely on watching the
Gazebo window alone.

## PHASE 19 — Visualization

Plot: drone trajectories, target position, distance-to-target, velocity,
each policy action, inter-agent distances, collision/safety thresholds.
The most useful first plot is usually distance-to-target vs time. For
multi-agent testing also plot minimum inter-agent distance vs time.

## PHASE 20 — Only then test the full system

```text
[1] checkpoint loads → [2] policy works in original environment →
[3] Gazebo works → [4] PX4 works → [5] ROS 2 ↔ PX4 works →
[6] deterministic command works → [7] coordinate frames verified →
[8] observation adapter verified → [9] action adapter verified →
[10] shadow-mode policy verified → [11] one-agent closed loop →
[12] two agents → [13] three agents → [14] four agents →
[15] randomized scenarios → [16] full evaluation
```

Never skip a failed stage.

## Debugging Rules for Claude

**Rule 1 -- Never make multiple architectural changes at once.** Change
one thing, run one test, collect evidence, interpret result, then change
the next thing. If several things change at once and it works or fails,
we learn almost nothing.

**Rule 2 -- Never say "it should work."** Replace "this should publish"
with `ros2 topic echo <topic>`. Replace "PX4 should receive it" with an
observable PX4-side confirmation. Replace "the observation should be
correct" with a comparison against the training observation. Everything
important must be experimentally verified.

**Rule 3 -- Never debug the RL policy first.** If ROS → PX4 → Gazebo has
not been proven independently, the neural policy is not the problem you
should investigate.

**Rule 4 -- Never silently change the training contract.** Do not change
observation ordering, normalization, clipping, action scaling, coordinate
frames, number of neighbours, agent ordering, or timestep unless the
change is intentional and documented.

**Rule 5 -- Always inspect actual topic types.** Never assume a topic is
`geometry_msgs/msg/Twist` or any other type -- use
`ros2 topic info <topic> --verbose` and inspect actual publishers/
subscribers. The same conceptual command can be exposed through different
message types.

**Rule 6 -- Keep the policy and simulator adapters separate.**

```text
stage_policy/policy.py
simulation_adapter/{observations.py, actions.py, frames.py}
ros2_interface/node.py
evaluation/{metrics.py, logging.py}
```

The trained policy should NOT contain Gazebo-specific code. The ROS node
adapts simulator data into the policy's expected interface.

## Definition of Done

The system is NOT successful because Gazebo opens, the drone appears, ROS
topics exist, the neural network loads, or actions are being printed.

The system is successful only when this loop operates repeatedly without
manual intervention:

```text
Gazebo state → correct observation → trained policy →
correct action conversion → PX4 → physical simulated response →
new correct observation
```

## Engineering Checklist

**Environment:** actual Ubuntu/ROS2/Gazebo/PX4/Python/PyTorch versions
recorded; correct workspace sourced; no accidental venv contamination; no
duplicate/conflicting ROS installations.

**Policy:** checkpoint loads; architecture exactly matches training;
observation dimension/ordering/normalization/clipping match; action
dimension/range match; policy works in the original training environment.

**Gazebo/PX4:** Gazebo starts cleanly; PX4 SITL starts cleanly; vehicle
spawns correctly; sensors update; PX4 estimator becomes healthy; no major
PX4/Gazebo errors; simulation time behaves correctly.

**ROS 2:** PX4 topics visible; correct topic types verified; ROS ↔ PX4
communication verified; `/clock` behaviour understood; `use_sim_time`
verified where required; no stale topics from another simulation; agent
namespaces verified.

**Observation adapter:** position/velocity/target/relative-target/distance
correct; neighbour and agent ordering correct; frames/signs/units/
normalization correct; no NaN/Inf; Gazebo distributions checked against
training.

**Action adapter:** meaning/frame/units documented; scaling/axis-order/
sign verified; artificial test actions verified; zero and +/- extremes
verified independently per axis.

**Closed loop:** shadow mode works; 1-agent test works; target tracking
works (distance decreases appropriately); 2/3/4-agent tests work; agent
identities remain correct; no cross-agent command routing; timing
measured; logs generated; trajectory recorded; metrics calculated.

## What Claude Should Do When Something Fails

Do NOT immediately rewrite the system. Produce this diagnostic:

```text
FAILURE:
<one sentence>

LAST VERIFIED STAGE:
<stage number>

FIRST UNVERIFIED INTERFACE:
<interface>

EXPECTED:
<what should happen>

ACTUAL:
<what happened>

EVIDENCE:
<commands/output/logs>

MOST LIKELY CAUSE:
<one or two causes>

NEXT SINGLE TEST:
<one experiment that distinguishes the causes>

DO NOT CHANGE:
<components that are currently known-good>
```

This prevents endless trial-and-error debugging.

## Final Principle

The trained model is only one component. Treat deployment as an
interface-validation problem, not as an RL problem. The goal is to prove
`TRAINING CONTRACT ≡ DEPLOYMENT CONTRACT` for observations, actions,
frames, units, timing, agent identity, normalization, and termination.
Only after those contracts match should we judge whether the learned
policy itself generalizes to Gazebo.
